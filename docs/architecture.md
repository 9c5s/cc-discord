# cc-discord の構成と設計

## 概要

`cc-discord` は、公式の discord channel plugin (`discord@claude-plugins-official`) の `server.ts` を取り込んで改変したプラグインです。
複数の Claude Code セッションが 1 つの Discord bot を共有しても、セッションごとに担当のチャンネルを分け、進捗を見やすく返せるようにします。
以下では、Discord から届いたメッセージを inbound、`reply` による返信の末尾に付ける情報ブロックを footer と呼びます。

拡張している振る舞いは次のとおりです。

- 担当チャンネル以外の inbound を扱いません。
  複数セッションによる重複処理を防ぐためです。
- inbound ごとに進捗用のスレッドを作成し、途中経過を transcript から転送します。
- 返信が返るまで、入力中の表示 (typing) を続けます。
- `reply` の末尾に、ブランチ、モデル、使用率を示す footer を付けます。
- すべての送信で、メンションの解決を無効にします。
- 送信系ツールの宛先を、担当チャンネルに限ります。
- 滞留した進捗スレッドを閉じます。
- 公式のプラグインに新しい版があれば、footer に印を出します。
  保守者向けで、環境変数で有効にします。

以前の構成は、公式の `server.ts` を無改変のまま起動し、Claude Code との stdio の間に挟んだ透過プロキシで拡張するもので、公式の更新に追随するまでの間は、起動したセッションが Discord に接続できませんでした。

現在の構成は、公式の `server.ts` をリポジトリに取り込み、拡張のロジックを呼び出す数行だけを加えたものです。
公式の更新は、手元の改変との 3-way マージで取り込みます。
取り込む時期は保守者が決めるため、公式の自動更新でセッションが Discord 無しになることはありません。
進捗を転送する処理は、以前は別プロセスの watcher でしたが、server のプロセスの中の周期処理になりました。
その結果、生存を知らせる heartbeat のファイルと、進捗の宛先を共有するファイルが不要になりました。

## 構成

```
cc-discord/                          (リポジトリ = marketplace)
  .claude-plugin/marketplace.json
  upstream/discord/                  素の公式ファイル (取り込み済みの版、配布しない)
  tools/upstream.ts                  上流の確認と取り込み (配布しない)
  docs/
  plugin/                            配布の単位
    .claude-plugin/plugin.json
    .mcp.json                        公式と同じ起動方法 (bun run --cwd ... start)
    .npmrc / package.json / bun.lock 公式に由来する
    server.ts                        公式を改変したもの
    upstream.json                    取り込み元、版、素の server.ts の SHA-256
    LICENSE / NOTICE
    hooks/hooks.json                 SessionStart のみ
    skills/access, skills/configure  公式を改変したもの (呼び名は /cc-discord:*)
    src/
      extension.ts                   拡張の組み立て (担当の判定、inbound の処理、進捗転送の周期処理、footer)
      discord-ops.ts                 discord.js への操作と、進捗用の REST クライアント
      discord-entity.ts              discord.js のチャンネルを、決定関数の入力の形へ変換
      routing.ts                     担当名、担当チャンネルの決定関数、配送と送信の判定、inbound の鮮度
      binding.ts                     自分の Claude Code の特定、ポインタの採否、channel の判定
      process-tree.ts                PID から、親の PID、作成時刻、起動引数を取得
      activation.ts                  現行 activation のポインタの読み書きと、古いポインタの削除
      session-start.ts               SessionStart hook
      inbound.ts                     inbound のロック、typing、進捗スレッドの作成
      progress.ts                    進捗の転送
      watch.ts                       transcript の増分の読み取りと、要約のまとめ方
      summarize.ts                   ツール呼び出しなどの要約、スレッド名
      stale-threads.ts               滞留スレッドの判定
      footer.ts / status.ts          footer の組み立て
      usage.ts                       使用量 API の取得とキャッシュ
      upstream-notice.ts             上流の印の判定
      log.ts                         拡張のログ
      ids.ts / normalize.ts / state-dir.ts / notify.ts   識別子の検証、名前の正規化、state dir、担当名とデバッグログ
    test/
```

配布の単位は `plugin/` だけです。
`marketplace.json` の `source` が `./plugin` を指しています。
依存は公式と同じく、起動時の `bun install --no-summary` で入ります。
`node_modules/` は gitignore の対象で、directory source で使う場合は、作業ツリーの `plugin/node_modules/` に入ります。

判定と状態を扱うモジュールは、純粋関数として切り出し、discord.js を import しません。
discord.js を import するのは、`server.ts` と `src/discord-ops.ts` だけです。
このため、担当の決定や配送の判定は、Discord に接続せずに検証できます。
チャンネル種別は、discord.js の列挙ではなく、数値 (`GuildText` は 0、`DM` は 1、スレッドは 10、11、12) で扱います。

`server.ts` は、トップレベルに副作用 (Discord への login と MCP の接続) があるため、単体テストの対象にしません。
このため、ロジックは `src/` に置き、`server.ts` からは呼び出すだけにします。

### 公式との関係

`upstream/discord/` には、取り込んだ時点の素の公式ファイルを置いています。
`upstream/discord/` と `plugin/` を比べると、改変した箇所が分かります。
公式は Apache License 2.0 です。
`plugin/LICENSE` に全文を置き、`plugin/NOTICE` に由来と改変の有無を記しています。
改変したファイル (`server.ts` と skills) の冒頭にも、改変した旨を記しています。
拡張のロジックを含むプラグイン全体も、Apache License 2.0 です。

### server.ts の改変箇所

改変は、拡張を呼び出す数行に絞ります。
上流との衝突を増やさないためです。

- import に、拡張のモジュールを足します。
- `instructions`、ペアリングの応答文、`fetchAllowedChannel` のエラー文に出てくる `/discord:access` を、`/cc-discord:access` に書き換えます。
- `fetchAllowedChannel` で、allowlist の判定を通過した後に、担当の判定を呼びます。
  担当外なら例外を投げます。
- `reply` で、宛先が分かった時点で typing を止めます。
  本文のチャンクに footer を結合し、各送信に `allowedMentions: { parse: [] }` を付けます。
- `edit_message` で、`allowedMentions: { parse: [] }` を付けます。
- `handleInbound` で、権限応答の判定 (`PERMISSION_REPLY_RE`) より後に、公式の 1 回だけの `sendTyping` を拡張の呼び出しに置き換えます。
  呼び出しの結果が偽なら、そこで処理を終えます。
- `client.once('ready')` と `shutdown` で、拡張の周期処理の開始と停止を呼びます。

担当の判定を権限応答の判定より後に置くのは、テキストによる権限応答を壊さないためです。
公式は権限の要求を `allowFrom` の利用者へ DM で送るため、応答 (`yes abcde`) も DM で届きます。
DM は `cc-discord` 担当のセッションにしか配送しません。
権限応答の判定より前に担当外の inbound を破棄すると、要求を出したセッションが DM の担当でない場合に、応答が届かなくなります。
公式の `gate` (allowlist、ペアリング、メンション必須の判定) は、担当の判定より前に残ります。
そのため、ペアリングの応答だけは、担当に関係なく全セッションから重複して送られます。

## 起動と接続

このリポジトリを marketplace として登録し、`cc-discord` を user scope でインストールします。
公式の `discord@claude-plugins-official` は無効にしておきます。
有効なままだと、公式の server が cc-discord の server とは別に起動し、担当の判定を経ない入力中の表示と受領リアクションを送ります。

channels は研究プレビュー中で、`--channels` に渡せるのは、Anthropic が維持する既定の allowlist に載ったプラグインか、managed settings の `allowedChannelPlugins` で承認したプラグインだけです。
cc-discord は第三者のプラグインなので、後者で承認します。
Windows では、`HKCU\SOFTWARE\Policies\ClaudeCode` の `Settings` (REG_SZ) に JSON 全体を置きます。
このキーは、HKLM とファイル版の managed settings が無いときだけ読まれるため、管理者権限が要りません。

```json
{
  "channelsEnabled": true,
  "allowedChannelPlugins": [
    { "marketplace": "cc-discord", "plugin": "cc-discord" }
  ]
}
```

`allowedChannelPlugins` は既定の allowlist を置き換えるため、公式の channel プラグインも使うなら、ここに併記します。
managed settings を 1 つでも置くと channels の既定が無効に変わるので、`channelsEnabled` は必ず `true` を明示します。

承認せずに `--dangerously-load-development-channels plugin:cc-discord@cc-discord` で起動することもできます。
ただし、対話セッションでは起動のたびに確認ダイアログが出ます。
承諾は永続化されません。

起動のたびに、`--channels plugin:cc-discord@cc-discord` を渡します。
シェルの関数にまとめておくと、渡し忘れを防げます。
PowerShell では次の形です。

```powershell
function claude {
  & "~/.local/bin/claude.exe" --channels plugin:cc-discord@cc-discord @args
}
```

この例には権限モードの指定を入れていません。
cc-discord が要求するのは `--channels` だけで、承認をどこまで省くかは環境ごとの判断になります。
承認を飛ばすモードで動かすなら、隔離した環境と専用のアカウントを用意します。
`access.json` と `allowedChannelPlugins` は、誰がどのチャンネルから話しかけられるかを絞るだけで、ツール実行の承認までは戻しません。

起動関数を書き換えたら、シェルを開き直してから起動します。
稼働中のシェルは、起動時に読んだ関数定義を保持し続けるためです。
古い関数のまま起動して `--channels` に cc-discord が渡らないと、channel が無効と判定され、server は inbound を一切扱いません。
症状は Discord に反応しないことだけですが、起動時のログに、判定の結果と根拠が 1 行残ります。

### 環境変数

| 変数 | 内容 |
| --- | --- |
| `CC_DISCORD_PROJECT_DIR` | 担当名を決めるディレクトリ (`CLAUDE_PROJECT_DIR` より優先し、別の担当を指すと稼働中のセッションと競合させずに検証できる) |
| `CC_DISCORD_CHANNEL` | channel の判定の上書き (`on` で有効、`off` で無効) |
| `CC_DISCORD_UPSTREAM_CHECK` | 空でなければ、上流の印を有効にする |
| `DISCORD_STATE_DIR` | state dir (公式と同じ変数で、絶対パスで指定する) |
| `DISCORD_NOTIFY_DEBUG` | 設定すると、SessionStart hook のデバッグログを書く |

`DISCORD_STATE_DIR` に相対パスを指定すると、プロセスごとに基準のディレクトリが異なります。
server は `bun run --cwd` でプラグインのディレクトリへ移って動作し、hook と skills は起動元のディレクトリで動作するためです。

## 各振る舞いの意図

### 担当チャンネルのルーティング

複数の Claude Code セッションが同じ bot に接続すると、server はすべてのセッションで起動して Gateway に接続するため、全セッションが同じメッセージを受け取ります。
拡張は、起動ディレクトリ名を正規化した担当名に一致するチャンネルの inbound だけを配送します。
正規化は、小文字化、空白とアンダースコアのハイフン化、英数字とハイフン以外の除去、連続したハイフンの統合、前後のハイフンの除去です。

担当チャンネルの決定関数は 1 つです。
`GuildText` で、正規化名が担当名に一致し、`access.json` の `groups` に登録済みの候補を、全 guild から集めます。
0 件なら未解決、2 件以上なら曖昧、1 件ならそれが担当です。
inbound の配送、送信系ツールの宛先、進捗の投稿の判定が、すべて同じ関数を使うため、結果が一致します。

guild とチャンネルの一覧は、REST ではなく、discord.js の Gateway のキャッシュから、判定のたびに組み立てます。
キャッシュは Gateway のイベントで更新されるため、チャンネルの改名や `access.json` の変更は、再起動なしで反映されます。
`access.json` は、公式の `loadAccess()` を拡張へ渡して読みます。
`DISCORD_ACCESS_MODE=static` のときも、公式と拡張が同じ snapshot を見ます。
discord.js のチャンネルは、決定関数が受け取る形 (`id`、`type`、`parent_id`、`recipients`) へ変換して渡し、決定関数は純粋関数のまま保ちます。

Gateway の `ready` より前は、キャッシュが空なので、担当は未解決です。
`messageCreate` は `ready` の後にしか発火しないため、inbound には影響しません。
起動直後に呼ばれた送信系ツールだけが失敗します。

判定できないときは、許可しません。
これを fail closed と呼びます。

- 担当ディレクトリがあるのに正規化名が空 (記号だけの名前など) なら、すべての inbound を扱いません。
- 候補が複数なら、inbound の配送と進捗の送信の両方を止めます。
- チャンネルの識別子の形式が不正なときも、扱いません。
- メッセージの生成から 1 時間を超えた inbound と、5 分より未来に見える inbound は、配送しません。
  配送の直前にも、同じ判定をやり直します。
- inbound のロックを取得できなかったときは、`EEXIST` もそれ以外の失敗も、扱いません。

担当ディレクトリが未設定のセッションでは、担当の判定もロックもせず、typing だけを開始して公式の処理を続けます。
単独運用の後方互換です。
DM の担当は、`cc-discord` という担当名のセッションだけで、guild の担当解決には依存しません。

### inbound の処理

`handleInbound` に差し込む処理の順序は次のとおりです。
各手順で配送しないと決めたら、そこで処理を終えます。

1. channel が無効なセッションでは、ここで処理を終えます。
   ロックを取得せず、typing も受領リアクションも送りません。
2. 担当名を持たないセッションでは、判定もロックも行わず、typing だけを開始して公式の処理を続けます。
3. 担当を判定します。
   `msg.channel` から決定関数で配送の可否を決めます。
   DM は `cc-discord` 担当のセッションだけが扱います。
4. 鮮度を判定します。
   `message_id` の生成から 1 時間を超えたものと、5 分より未来に見えるものを配送しません。
5. ロックを取得します。
   `progress-thread/<owner>.lock-<message_id>` を排他作成し、取得できなければ配送しません。
   取得できなかったセッションも処理すると、重複して返信しうるためです。
6. typing を開始します。
   8 秒ごとに送り直し、`reply` で止め、10 分で必ず止めます。
7. 現行 activation があれば、進捗スレッドを作成します。
8. 鮮度を再判定します。
   配送しない場合は、typing も止めます。
9. 宛先をメモリに設定し、続けて `mcp.notification` で配送します。

受領リアクションと添付の一覧は、公式の実装をそのまま使います。
同じプロセスの中では、inbound の処理を直列に並べ、ロックの取得と宛先の設定の順序を保ちます。
ロックの回収は、60 秒ごとの周期処理で行います。

### typing の継続

Discord の入力中の表示は、送信から約 10 秒で自動的に消えます。
公式は inbound の受信時に 1 回だけ送るため、返信の生成が 10 秒を超えると途中で消えます。
拡張は、ロックを取得したセッションだけが 8 秒ごとに送り直し、返信まで表示を続けます。

停止は、`reply` が宛先の `chat_id` を受け取った時点で、他の検証より先に、無条件で行います。
連続した入力の途中で表示がいったん消えるトレードオフはありますが、一般的な bot の挙動として違和感は小さいです。
安全弁として、10 分で必ず停止します。

### 自分の Claude Code の特定

server は、起動時に自分の Claude Code のプロセスを 1 回だけ特定し、PID、作成時刻、起動引数を取得します。
Claude Code は server が存続している間は終了しないため、取得は起動時の 1 回で足ります。
channel の判定とポインタの採否は、この 1 つのプロセスだけで行います。
Claude Code の中で Claude Code を起動した入れ子の構成で、外側のプロセスの起動引数やポインタを、内側のセッションが使わないためです。

公式と同じ起動方法 (`bun run --cwd <プラグインのディレクトリ> --shell=bun --silent start`) では、`server.ts` の親は Claude Code ではなく、中間の `bun run` です。
起動方法を独自のものに変えれば Claude Code の直接の子にできます。
しかし、`.mcp.json` と `package.json` が恒久的に上流とずれ、上流が起動方法を変えるたびに衝突するため、採りません。

そこで server は、祖先を親から順に最大 6 段たどり、起動の中継だけを飛ばして、最初に現れたそれ以外のプロセスを自分の Claude Code とみなします。
中継とみなすのは、起動引数に `run` があり、かつ `--cwd` の値がプラグインのディレクトリ (`CLAUDE_PLUGIN_ROOT`) と一致するプロセスだけです。
比較は実体のパスで行い、Windows では大文字小文字を区別しません。
最初に現れた中継以外のプロセスで探索を打ち切り、その先の祖先へは進みません。

起動引数のどこかにプラグインのディレクトリを含むかどうかで判定すると、`--plugin-dir` でそのディレクトリを渡した Claude Code 自身や、プロンプトの本文にパスを含む起動まで中継とみなし、外側の Claude Code を採用しうるためです。
中継と Claude Code の間に別のプロセス (シェルなど) が挟まった場合は、そのプロセスを Claude Code とみなします。
そのプロセスはポインタも channel のフラグも持たないため、進捗転送と channel が無効になります。

プロセスの情報は、OS ごとに取得する関数 (`src/process-tree.ts`) を 1 つ用意しています。
PID から、存在しない、存在して取得できた、存在するが取得に失敗した、のいずれかを返します。
存在の判定は `process.kill(pid, 0)` で行い、`ESRCH` を存在しない、成功と `EPERM` を存在するとみなします。

- Windows では、bun:ffi で `OpenProcess`、`NtQueryInformationProcess` (情報クラス 0 で親の PID、60 で起動引数)、`GetProcessTimes` を呼びます。
- Linux では、`/proc/<pid>/stat` (親の PID と起動時刻)、`/proc/stat` の `btime`、`/proc/<pid>/cmdline` を読みます。
- macOS では、`ps` を使います。

自分の Claude Code を特定できない環境では、進捗転送と footer のモデル行を無効にします。
送信系のツールは動作します。
channel は無効と判定されるため、inbound を扱うには `CC_DISCORD_CHANNEL=on` で上書きします。

### channel が無効なセッションの扱い

プラグインが有効なら、Desktop、resume daemon、`--channels` を付けない起動でも、server は起動して Discord に接続し、inbound を受けます。
しかし、そのセッションでは channel が登録されていないため、Claude Code は通知を Claude に渡しません。
こうしたセッションがロックを先に取得すると、その inbound は失われます。
さらに、スレッドの作成と進捗転送を抑えなければ、inbound のたびにスレッドを作り、自分の無関係な作業をそこへ転送します。

MCP の初期化の内容は、channel の有無で変わりません。
2026-11-19 に、検証用の MCP サーバーを `--dangerously-load-development-channels` の有無で 2 回起動し、`initialize` の要求が同一であることを確認しました。
server は、MCP のやり取りから channel の有無を知ることができません。

そこで、自分の Claude Code の起動引数で判定し、channel が無効なセッションでは inbound を一切扱いません。
ロックも取得しないため、無効なセッションのせいで、他のセッションの inbound が失われることもありません。
判定は、`--channels` または `--dangerously-load-development-channels` の値に、このプラグインを指す `plugin:cc-discord@<marketplace>` が含まれているかどうかです。
環境変数 `CC_DISCORD_CHANNEL` に `on` か `off` を設定すると、判定を上書きできます。

判定の結果と根拠 (どの PID のどの引数か、または上書き) は、起動時にログへ 1 行出します。
自分の Claude Code を特定できないか、起動引数を取得できない環境では、無効と判定し、上書きの環境変数を案内するログを出します。

ロックを全セッションで取得し、判定を typing とスレッドの作成だけに使う方式は、判定を誤っても進捗が出ないだけで済みます。
しかし、無効なセッションが inbound を失わせる問題が残るため、採りませんでした。
判定しない方式は、無関係な作業の転送が起きるため、候補から外しました。
採用した方式には、将来 Claude Code がフラグ以外の方法で channel を有効にできるようになると、判定を誤って inbound を扱わなくなる危険があります。
上書きの環境変数と起動時のログは、これに備えたものです。

### 進捗スレッド

途中経過を親チャンネルへ直接投稿すると、会話の本筋に埋もれます。
このため、inbound ごとにスレッドを作成し、そこへ転送します。
`reply` による返信は、従来どおり親チャンネル (または DM) へ送ります。

スレッドを作成するのは、現行 activation を解決できたときだけです。
自分の Claude Code を特定できない環境や、SessionStart hook がポインタを書けなかったセッションでは、進捗を転送できません。
そこでスレッドだけ作成すると、誰も使わない空のスレッドが inbound のたびに残ります。

スレッドは、bot 自身がゼロ幅スペース (U+200B) 1 文字を通知抑止フラグ付きで投稿し、そのメッセージから public スレッドを作成する方式で作ります。
inbound 自体をアンカーにすると、作者であるユーザーがスレッドの参加者になり、フォロー通知が付きます。
private スレッドにすると、閲覧に管理権限が要ります。
bot の投稿をアンカーにすると、どちらも避けられ、親チャンネルに「スレッドを開始しました」のシステム行も出ません。
アンカーをゼロ幅スペースにするのは、半角空白と NBSP は Discord 側で除去されますが、ゼロ幅スペースは残るためです。
アンカーの投稿には、通知抑止フラグ (`1 << 12`) を付けます。

スレッドの自動 archive は 60 分、名前は `[MM/DD HH:MM] <本文>` です。
本文は連続した空白を 1 つに正規化し、80 字を超えたら 79 字に切って末尾に省略記号を付けます。
本文が空のときは `progress` とします。
アンカーかスレッドの作成に失敗したときは、親チャンネル自身を宛先にします。
進捗が全く出ないより、親チャンネルへ直接出るほうを選ぶためです。

DM にはスレッドを作成できないため、DM チャンネル自身を宛先にします。
スレッド内の inbound は、そのスレッドをそのまま宛先にします。

### 担当外への送信の遮断

公式の `access.json` は、ペアリング済みのチャンネルをすべて許可する単一の allowlist です。
これだけを条件にすると、あるプロジェクトのセッションから、同じ bot に登録された別プロジェクトのチャンネルへ、返信も履歴取得もできてしまいます。
担当の分離が inbound 側にしか効かないことになります。
Discord のメッセージ本文は外部入力なので、別チャンネルの id を指す指示が紛れ込む経路も、現実に存在します。

そこで、担当の判定を `fetchAllowedChannel` の中で行います。
公式のツールのうち、宛先を引数に持つ次の 6 つは、すべてこの関数を経由します。

| ツール | 引数 |
| --- | --- |
| `reply` | `chat_id` |
| `edit_message` | `chat_id` |
| `react` | `chat_id` |
| `download_attachment` | `chat_id` |
| `fetch_messages` | `channel` |
| `create_thread` | `chat_id` |

ツールごとの一覧は持ちません。
上流が追加したツールも、この関数を経由する限り、自動で対象になります。
この関数を経由せずに宛先を扱うツールが上流に追加された場合に備え、取り込みの手順に確認の項目を設けています。

判定は inbound と同じ決定関数で行い、allowlist の判定を通過した後に重ねます。
このため、配送を許す宛先と、送信できる宛先が、常に一致します。

- チャンネルの実体を取得できない、id が要求と違う、担当チャンネル (スレッドなら親) と一致しない場合は、送りません。
- DM は、`cc-discord` 担当のセッションだけが送れます。
  inbound と同じ規則です。
- 担当ディレクトリが未設定のセッションでは、判定しません。
  単独運用の後方互換です。

担当が未解決または曖昧なセッションでは、guild 宛の送信がすべて失敗します。
これは意図した fail closed で、担当を復旧するまで送信できません。

### reply と edit_message

公式の実装をそのまま使います。
公式の実装に足すのは、次の 3 点だけです。

- 宛先の `chat_id` を受け取った時点で、他の検証より先に typing を止めます。
- footer を本文とは別に組み立て、末尾のチャンクに改行 1 つを挟んで収まるなら結合し、収まらなければ独立したチャンクとして足します。
  チャンク分割がコードブロックの終端を分断しないようにするためです。
- すべての送信に `allowedMentions: { parse: [] }` を付けます。

公式の `noteSent` がそのまま動作するため、メンション必須のチャンネルで、bot への返信をメンションとみなす短絡も機能します。

### メンション解決の無効化

コードブロックやインラインコードの中の `@everyone` や `<@USER_ID>` は、表示上は素のテキストのままでも、Discord API がメッセージ全体から解析して通知を発生させます。
コードによる装飾は防御にならないため、拡張が送るすべてのメッセージ (reply、edit_message、進捗、アンカー) に、`allowedMentions: { parse: [] }` (進捗の REST では `allowed_mentions: { parse: [] }`) を付けます。
詳細は `docs/discord-text-formatting.md` に記録しています。

`allowedMentions` を指定すると、引用返信の相手への通知も、既定で無効になります。

### reply 末尾の footer

返信の末尾に、ブランチ名、モデル名と effort、コンテキスト使用率、5 時間枠と 7 日枠の使用率を、コードブロックで付けます。
値は、次の経路で集めます。

- ブランチは、担当ディレクトリの `.git/HEAD` を直接読みます。
- モデル、effort、コンテキスト使用量は、採用したポインタの transcript の末尾から、直前のターンの assistant エントリを逆順に探して読みます。
- コンテキストの分母は、モデルによらず 1,000,000 とします。
  1M を標準で持たない世代 (Claude 4 系の 4.6 以前) は使わない前提で、settings の `model` は読みません。
- 5 時間枠と 7 日枠とモデル別枠は、`reply` の時点で使用量 API から取得します。
  全セッション共通で直近 60 秒以内に試行済みの場合と、取得に失敗した場合は、最後に取得できた値をキャッシュから使います。
  リセット時刻を過ぎた枠は省きます。

採用したポインタが無い場合は、モデル行とコンテキスト使用率を省き、ブランチと使用量だけで作ります。
別のセッションや別の起動の値を出さないためです。

使用量 API の取得は、返信の送信を待たせるため、タイムアウトを 3 秒にしています。
背景で定期的に取得してキャッシュを読む方式は、表示が直前の取得時点の値になるため採りません。
試行の間隔に 60 秒の下限を設けるのは、使用量 API が Claude Code 本体や statusline と上限を共有しており、短い間隔で呼ぶと 429 を返すためです。
試行時刻は取得の前にキャッシュへ記録し、並行して動作するセッションの重複した取得を減らします。
試行時刻を記録できなかった場合は、60 秒の下限を守れないため、取得せずにキャッシュの値を使います。

#### 上流の印

環境変数 `CC_DISCORD_UPSTREAM_CHECK` が空でないときだけ、footer の最後の行に上流の印を出します。
公式 marketplace のクローン (`<Claude の設定ディレクトリ>/plugins/marketplaces/claude-plugins-official/external_plugins/discord/`) の `server.ts` の SHA-256 を、`plugin/upstream.json` に記録した取り込み済みの版の hash と比べます。
違えば、同じディレクトリの `.claude-plugin/plugin.json` の `version` を添えて、`upstream <版>` と出します。
クローンはプラグインを無効にしていても自動で更新されるため、取り込むかどうかを保守者が決める合図になります。
クローンが無い環境や、読み取りに失敗した環境では、印を出しません。

合図を footer に出す方式にしたのは、通知を 1 回だけ送る方式ではどのセッションが送るかの調整が要り、確認を手で行う方式では気付くかどうかが運用に依存するためです。
利用者は上流との差分を自分で取り込めないため、印は保守者だけに出し、環境変数で有効にします。

### 滞留スレッドの archive

進捗スレッドは、自動 archive を 60 分にして作成しますが、Discord 側の自動 archive が発火しないまま滞留する事例があります。
拡張は、`ready` の直後と 5 分ごとに、担当チャンネル配下の稼働中スレッドを discord.js で取得し、次の条件をすべて満たすものだけを閉じます。

- 親が担当チャンネルである。
- bot 自身が作成した。
- 名前が `[MM/DD HH:MM]` で始まる。
- 自動 archive が 60 分である。
- 最終メッセージまたは作成から 13 時間以上経過している。
- 自分の現在の宛先ではない。

条件を緩めると、同じチャンネル内の他用途のスレッドを誤って閉じうるため、6 条件の AND を維持します。

13 時間という閾値は、宛先の有効期間 (12 時間) より 1 時間長くしています。
宛先はプロセスごとのメモリにあるため、他のセッションの宛先は参照できません。
閾値を宛先の有効期間より長くすることで、有効な宛先が残っているスレッドを閉じないようにしています。

自分の現在の宛先かどうかは、スレッドごとに、閉じる直前に確認します。
一覧の取得や先のスレッドの archive を待つ間に、古いスレッドの中の inbound でそのスレッドが宛先になることがあるためです。
前の回が終わる前に次の周期が来たときは、その回を行いません。

## 進捗転送の仕組み

進捗の転送は、activation に紐付けます。
activation とは、1 回の SessionStart (`startup`、`resume`、`clear`、`fork`) で始まる期間で、hook が生成する `activation_id` で識別します。
compaction は同じ作業の継続なので、activation を変えません。

- SessionStart hook が、Claude Code の PID ごとに、現行 activation のポインタを書きます。
- server は、自分の Claude Code のポインタだけを採用し、その activation の transcript を監視します。
- 進捗の宛先はメモリ上の 1 件で、inbound のたびに server が設定します。

### ポインタ

ポインタは `session/by-pid/<claude_pid>.json` に置き、次の項目を持ちます。

| 項目 | 内容 |
| --- | --- |
| `claude_pid` | Claude Code の PID |
| `claude_started_at` | Claude Code のプロセスの作成時刻 (epoch ミリ秒) |
| `session_id` | セッション ID |
| `activation_id` | activation の識別子 |
| `transcript_path` | transcript のパス |
| `source` | SessionStart の種別 |
| `written_at` | 書き込み時刻 |
| `model` | モデル名 (任意) |

`activation_id` は、`compact` で同じ `session_id` のときだけ維持し、それ以外の SessionStart では新しく生成します。
新しい activation では、旧ポインタを削除してから新ポインタを書きます。
失敗したときに、古い activation の進捗が残るより、進捗が欠けるほうを選ぶためです。

hook が `CLAUDE_PID` のプロセスの作成時刻を取得できなかった場合は、`claude_started_at` を書きません。
server は、`claude_started_at` の無いポインタを採用しません。

server が採用するのは、`session/by-pid/<自分の Claude Code の PID>.json` のうち、`claude_started_at` が自分の Claude Code の作成時刻と一致するポインタだけです。
ポインタが無いか一致しない間は、他の祖先のポインタへ移らず、進捗転送を行いません。

#### PID の再利用への備え

PID と作成時刻の組は、存在しているプロセスを一意に識別します。
終了したプロセスが残したポインタを、同じ PID を再利用した新しいプロセスが自分のものとして読む誤りは、この組の一致で防ぎます。

Claude Code のセッション ID は、代わりになりません。
2026-11-19 に Windows で稼働中のプロセスの環境を読んで確認したところ、MCP サーバーの `CLAUDE_CODE_SESSION_ID` は、MCP を起動した時点のセッションに固定されていました。
`claude --resume` で起動したプロセスでは、再開したセッションとは別の ID が入っていました。
一方、hook の `CLAUDE_CODE_SESSION_ID` は `/clear` に追随します。
`CLAUDE_CODE_MESSAGING_SOCKET` は公開されていない内部の変数なので、安全境界には使いません。

ポインタの書き込み時刻と作成時刻の前後で比べる方式は、採りません。
時計の揺れを吸収する許容幅が要り、その幅の内側で書かれた古いポインタを採用してしまうためです。

#### 古いポインタの削除

hook は、ポインタを書いた後に、古いポインタを削除します。
消すのは、プロセスが存在しない PID のポインタと、プロセスは存在するが作成時刻が `claude_started_at` と一致しないポインタです。
後者は、PID が再利用されたものです。
`claude_started_at` を持たない旧形式のポインタは、作成時刻が `written_at` より後なら、再利用とみなして消します。
プロセスの情報の取得に失敗しただけのものは、プロセスが無いと判定できないため、残します。
自分の PID のポインタは消しません。

hook が消すのは、`.json` のポインタだけです。

### 周期処理

進捗の転送は、server のプロセスの中の周期処理です。

- 毎秒ポインタを読み、`activation_id` が変わったら、宛先を消し、新しい transcript の末尾を読み取り位置にします。
- 250 ms ごとに、transcript の増分を読みます。
  宛先が無い間は、読み取り位置だけを進めます。
  宛先がある間は、assistant の text、thinking、tool_use を要約してまとめ、宛先へ投稿します。

tool_use も、transcript から読んで同じ経路で送ります。
PreToolUse hook からの即時送信は、assistant メッセージの transcript への書き込みより早く発火するため、text との並びが逆転します。
経路を transcript に一本化することで、content の順序を Discord の表示順に保ちます。

投稿は、通知抑止フラグ (`1 << 12`) と `allowed_mentions: { parse: [] }` を付けて送り、1 回の投稿は 1900 コードポイントまでです。
投稿の直前に、宛先が今も担当の判定を通過することを、Gateway のキャッシュで確認します。
DM は、相手が `allowFrom` にあることも確認します。
通過しなければ、送りません。

1 回の読み取りで得たチャンクの列は、読み取りを始めた時点の宛先と activation に結び付けます。
各チャンクの送信の直前に、宛先と activation が変わっていないことを確認し、変わっていれば残りを破棄します。
送信を待つ間に、次の inbound や activation の切り替えが起きても、前のやり取りの進捗を新しい宛先へ送らないためです。
宛先を新しく設定したときは、読み取り位置を transcript の現在の末尾へ進め、持ち越していた行の断片を捨てます。
設定までに書かれてまだ読んでいない行も前のやり取りの進捗なので、新しい宛先へ送りません。

### 進捗用の REST クライアント

進捗の投稿だけは、discord.js のクライアントとは別に、レート制限で待たずに例外を投げる REST クライアントを使います。
discord.js の既定の REST は、429 と事前の流量制御を内部で待ってから送ります。
待ちの間に activation や担当や allowlist が変わっても、待つ前の判定のまま投稿してしまうためです。

`@discordjs/rest` の `rejectOnRateLimit` を、常に真を返す関数にすると、待たずに `RateLimitError` (待ち時間 `retryAfter` を持つ) を投げます。
ただし `@discordjs/rest` は、既定値 `retries: 3` のもとで、タイムアウト、接続の切断、5xx の応答に対して、3 回まで自動で送り直します。
この再送も判定を経ずに古い本文を送るため、進捗用の REST クライアントには `retries: 0` も指定し、送り直しを進捗転送の側の判断に限ります。
discord.js は `@discordjs/rest` をそのまま再公開しているため、依存を足す必要はありません。

429 を受けたら、待ち時間が 10 秒以内なら、待ってから宛先、activation、送信可否を再確認して、1 回だけ送り直します。
10 秒を超えるなら、送りません。
429 以外の失敗は、送り直さずに、そのチャンクを諦めます。

### 宛先の有効期間

宛先はメモリ上の 1 件で、終わるのは次の 4 つの場合です。

1. 次の inbound による上書き
2. activation の切り替え
3. 設定から 12 時間
4. server の終了

`reply` では、宛先を終わらせません。
Claude は途中経過を返信してから作業を続けることが多く、返信の後の作業こそスレッドで確認したいためです。

MCP だけが再起動された場合 (`/reload-plugins` や `/mcp reconnect`) も、ポインタは引き続き有効なので、新しい server は transcript の監視を再開します。
ただし、メモリ上の宛先は失われるため、進行中のターンの進捗は、次の inbound まで止まります。

## ファイル契約 (state dir)

state dir の既定は `~/.claude/channels/discord` で、`DISCORD_STATE_DIR` があればそれを使います。
公式が使う `access.json`、`.env`、`approved/`、`inbox/` は、そのままです。
拡張が読み書きするのは、次のファイルです。

| パス | 内容 |
| --- | --- |
| `access.json` | 公式のアクセス制御 (拡張は読むだけ) |
| `session/by-pid/<claude_pid>.json` | 現行 activation のポインタ (SessionStart hook が書く) |
| `progress-thread/<owner>.lock-<message_id>` | inbound の排他ロック (12 時間より古いものを、60 秒ごとの周期処理で回収する) |
| `logs/cc-discord-<owner>.log` | 拡張のログ (担当名を持たないセッションは `logs/cc-discord.log`) |
| `logs/watch-<owner>.log` | SessionStart hook のデバッグログ (`DISCORD_NOTIFY_DEBUG` を設定したときだけ書く) |
| `model-usage.json` | 使用量 API のキャッシュと試行時刻 |

ポインタと `model-usage.json` は、PID 付きの一時ファイルへ書いてから rename します。
ファイル名に埋める識別子は、形式を検証し、解決後のパスが対象ディレクトリの直下であることを確認してから、読み書きします。

ロックは `openSync(path, 'wx', 0o600)` で作成します。

拡張のログには、次の内容を常時追記します。

- 配送しなかった inbound と、その理由 (channel が無効な場合を含む)
- 担当外の宛先への送信を止めたことと、その理由
- channel の判定の結果と根拠 (起動時に 1 行)
- 進捗スレッドの作成の失敗と、現行 activation が無いためにスレッドを作成しなかったこと
- 進捗の宛先の確認の失敗と、進捗の送信の見送りと失敗
- 閉じた滞留スレッドの件数
- 周期処理の失敗

ログの書き込みに失敗しても、本体は止めません。

server の終了処理は、ポインタを消しません。
MCP だけが再起動される経路では SessionStart が発火せず、誰もポインタを作り直さないためです。
消すと、実行中のターンの進捗が止まり、以後の inbound も進捗を転送できません。
残っていても誤用は起きません。
PID と作成時刻の両方が一致しない限りポインタは採用されず、残ったポインタは、次の SessionStart による置き換えか、古いポインタの削除で取り除かれます。

## 上流の取り込み手順

公式 marketplace のクローンは、プラグインを無効にしていても自動で更新されます。
cc-discord は、取り込むまで更新されないため、取り込む時期は保守者が決めます。

取り込みは、`tools/upstream.ts` の 2 つの操作で行います。
どちらも、引数に公式の discord ディレクトリを渡せます。
省略すると、公式 marketplace のクローンを使います。

- `bun tools/upstream.ts check`: 公式のディレクトリを `upstream/discord/` と比べ、版と変わったファイルを表示します。
- `bun tools/upstream.ts merge`: 追跡対象のファイルごとに、`git merge-file -p plugin/<f> upstream/discord/<f> <新版>/<f>` で結果を得て、取り込みます。

追跡対象は、配布物に含める公式由来のファイル (`server.ts`、`package.json`、`.npmrc`、`.mcp.json`、`LICENSE`、`skills/access/SKILL.md`、`skills/configure/SKILL.md`) です。
`bun.lock` はマージせず、新版を `upstream/discord/` と `plugin/` へ写します。
上流に新しく現れたファイルは、取り込むかどうかを保守者が決められるよう、一覧で報告します。
`README.md` と `ACCESS.md` は、報告の対象外です。

`merge` は、すべてのファイルでエラーが無いことを確認してから、`plugin/` に結果を書き、`plugin/upstream.json` を更新し、最後に `upstream/discord/` を新版で置き換えます。
衝突したファイルは、衝突マーカーを `plugin/` 側に残して報告し、非 0 で終わります。
衝突があっても、`upstream/discord/` と `plugin/upstream.json` は新版に更新されます。

`git merge-file` の終了コードは、0 が衝突なし、1 から 127 が衝突の数です。
それ以外 (エラーは 255 になります) と、起動の失敗は、エラーとして扱います。
エラーを衝突として扱うと、取り込めていないまま基準の版だけが進み、次の取り込みで差分を失うためです。

`git merge-file` のエラーと、書き込みの前に行う次の検査のエラーのときは、`plugin/`、`upstream/discord/`、`plugin/upstream.json` のどれも変更しません。

- 新版の版を読めるか。
- 新版に追跡対象がそろっているか。
  `plugin/` にある追跡対象が、取り込み済みの版にあるか。
- 取り込み元が、`upstream/discord/` と `plugin/` のどちらとも重ならないか。
  同じディレクトリ、その中のディレクトリ、それを含むディレクトリを、重なりとみなします。
  リンクは解決してから比べ、Windows では大文字と小文字を区別しません。

`merge` は、次の順に進みます。

1. 取り込み元が重なっていないかを、元のパスで確認します。
2. `upstream/discord.tmp/` を作り、取り込み元を `node_modules` と `.git` を除いて写します。
   版の読み取り、新しく現れたファイルの検出、マージ、`bun.lock` とハッシュの読み取り、次の基準の版の用意は、すべてこの写しから行います。
   写しの作成からここまでに失敗したときは、作った `upstream/discord.tmp/` を消して終わるため、何も変わりません。
3. `plugin/` に結果を書き、`plugin/upstream.json` を更新します。
4. 旧版の `upstream/discord/` を `upstream/discord.tmp/` の中へ rename で退避し、次の基準の版を `upstream/discord/` へ rename してから、`upstream/discord.tmp/` を消します。

取り込み元を最初に写すのは、取り込みの途中で公式 marketplace のクローンが更新されても、`plugin/`、`upstream/discord/`、`plugin/upstream.json` を、取り込みを始めた時点の同じ版にそろえるためです。
取り込み元を別々の時点で読むと、`plugin/` は古い版のまま基準の版だけが新しい版になり、やり直しても新しい変更が `plugin/` に入りません。
基準の版を最後に入れ替えるのは、3 の途中で失敗しても、取り込む前の基準の版を残すためです。
ただし、3 と 4 の途中で I/O が失敗すると、部分的に変更されたまま終わることがあります。
取り込みは作業ブランチで行うので、`git status` で変更を確認し、`git checkout` で戻すか、同じ取り込みをやり直します。
やり直しでは、`plugin/` にすでに書かれた変更が新版の変更と同じになるため、その部分は衝突しません。
`upstream/discord.tmp/` が残っていると、`merge` は何も変更せずに失敗します。
`upstream/discord/` を `git status` で確認し、必要なら `git checkout` で戻してから、`upstream/discord.tmp/` を消します。

手順は次のとおりです。

1. 新しい版を検知します。
   footer の印 (`CC_DISCORD_UPSTREAM_CHECK`) か、`check` で分かります。
2. 作業ブランチを作り、`merge` を実行します。
   衝突を解消してから、`plugin` ディレクトリで `bun install` を実行し、`bun.lock` と依存を整えます。
   `package.json` に衝突マーカーが残っていると、`bun install` が失敗するためです。
3. 上流の差分を読み、次の 3 点を確認します。
   - 宛先を引数に持つ新しいツールが、`fetchAllowedChannel` を経由しているか。
   - 改変箇所の前提 (たとえば、権限応答の判定の位置) が崩れていないか。
   - `.mcp.json` の起動構造 (`bun run --cwd <プラグインのディレクトリ>`) が変わっていないか。
     自分の Claude Code を特定する判定が、この構造に依存しています。
4. `plugin` で `bun test`、リポジトリ直下で `bun test ./tools` を実行し、成功を確認してから、PR を作成してマージします。
5. 作業ツリーを更新し、各セッションを順に再起動します。
   directory source の marketplace は、作業ツリーの内容が、次に起動するセッションの挙動になります。
   稼働中のセッションは、再起動するまで古い server のままです。

## レビューでの判断記録

外部レビューで指摘され、検証のうえで反映しなかった事項を残します。
同じ指摘を繰り返さないための記録です。

### permission relay は公式のまま残す

`notifications/claude/channel/permission_request` を破棄する案がありました。
公式はこの通知を受けると、`access.allowFrom` の全ユーザーへ DM でボタンを送り、返ってきた操作を Claude Code へ中継します。
公式の実装のコメントには、権限の要求をグループへ送らない理由が、single-user mode for official plugins という方針として明記されています。
`allowFrom` の利用者は、明示的なペアリングを経た者だけです。

フォークは、この前提を覆す立場にありません。
破棄すると、公式の機能を一方的に無効にすることになるため、公式の実装のまま残します。
`allowFrom` に複数の利用者を登録した場合、権限要求の内容が全員に見え、誰でも応答できる点は、公式の仕様のままです。
ボタンの操作は Gateway 経由で全セッションの server に届きますが、`request_id` が一致しないセッションの応答は、Claude Code 側で無視されます。

### inbound ロックの回収は年齢だけで判定する

回収までの時間を 60 秒にすると、直列の待ちの間にロックが回収され、二重に返信しうるため、12 時間にしています。
inbound の処理は 1 プロセスの中で直列に並ぶため、直前の inbound のスレッド作成が長引くと、次の inbound は待たされてからロックを取得します。
その待ちの間に別のプロセスが同じ inbound を処理し、さらに別の inbound の処理でロックを回収すると、待たされていたプロセスがロックを取り直して、二重に返信するおそれがあります。

処理済みの `message_id` を別に記録する仕組みは持たず、ロックファイル自体が 12 時間残ることで、処理済みの印を兼ねます。
回収は、異常終了で残ったファイルの削除だけを目的とするもので、処理の完了を保証する時間ではありません。
同じ `message_id` の inbound が 12 時間後に再び届くことは事実上ないため、回収を遅らせても取りこぼしは起きません。

ただし、時間だけを根拠にすると、12 時間を超えて待たされた inbound を排除できません。
そこで、inbound 側にも鮮度の上限を設けています。
上限と判定の位置は、「inbound の処理」の手順 4 と 8 のとおりです。
未来側にも上限を置くのは、時計が大きく遅れた環境で、古い inbound が新しく見えるためです。
判定を 2 回行うのは、スレッドの作成を待つ間に鮮度が切れることがあるためです。
宛先の設定を 2 回目の判定の後にするのは、配送されない inbound の宛先を、進捗転送から参照させないためです。

ロックは作成から 12 時間残り、inbound は生成から 1 時間で受け付けなくなります。
ロックの作成は必ずメッセージの生成より後なので、回収された後にその inbound が処理されることはありません。
2 回目の判定と配送の間には待ちが無いため、判定を通過した inbound だけが配送されます。
古い inbound をそもそも配送しないのは、長く止まっていたプロセスが再開したときの挙動としても正しいです。

### 添付に独自の検査と上限を足さない

25MB 弱のファイルを 10 個添付されると、multipart を組む前に 250MB 近いバッファを抱える、という指摘がありました。
通常ファイル以外の添付を、読み取る前に断る検査を足す案もありました。

Claude が `reply` に付けるのは、スクリーンショットや抜粋したログで、この規模にはなりません。
仮に届いても、Discord は 1 メッセージのリクエスト全体を 25 MiB で制限するため、送信は成功しません。
`reply` の添付の扱いは公式の実装のままで、そこへ独自の検査や上限を足すと、同じ入力に対する挙動が公式と分かれます。
上流との衝突も増えるため、足しません。

### access.json の更新にロックを導入しない

`access.json` を書くのは、`/cc-discord:access` と、`pairing` の `pending` を保存する公式の server の 2 者です。
`/cc-discord:configure` は読むだけです。
どちらも、読み込みから書き戻しまでの間に相手の更新を取りこぼしうるため、共有ロック付きの更新境界へまとめるべき、という指摘がありました。

access の管理はこの 2 者の領分で、拡張は読むだけです。
片方だけがロックを守っても競合は消えず、公式に由来する skill に規約を足すと、上流が変わるたびに追随する対象が増えます。
競合の窓は、ペアリングの承認と未知の DM の到着が重なるときに限られ、取りこぼされた側は、もう一度ペアリングすれば復旧します。

### 使用量の試行間隔の判定に排他を導入しない

試行間隔の確認と試行時刻の記録が排他になっておらず、複数のプロセスが同時に使用量 API を取得しうる、という指摘がありました。

確認から記録までは同期的なファイル操作だけで、間に `await` を挟まないため、競合の窓はミリ秒の単位です。
別々のセッションの返信がこの窓に重なる頻度は低く、重なっても、余分な取得が 1 回増えるだけです。
429 を招くような頻度の呼び出しにはなりません。
使用量キャッシュのファイルロックは、同時に実行された更新どうしが上書きし合っても同時点の値なので害が無いことから、一度撤去しています。
そのため排他は持たず、文書とコメントの記述を「重複した取得を減らす」にしています。

### typing に ref-count を持たせない

同じチャンネルで inbound が重なると、先に来た方の返信で入力中の表示が消えます。
チャンネルごとの残数を持てば、後から来た方の処理中も表示を続けられる、という指摘がありました。

残数方式には、返信されないターンで残数が減らないという欠点があります。
Claude Code の処理は中断できるため、`reply` が呼ばれないまま終わるターンは珍しくありません。
その分の残数は誰も減らせず、安全弁の 10 分まで入力中の表示が残ります。

どちらの方式にも、表示が実態とずれる場面があり、ずれる向きが違うだけです。
「処理中なのに消える」より「処理していないのに出続ける」ほうが誤解を招くため、無条件に停止する側を選んでいます。

### ログは debug の設定で絞らない

複数セッションが同じ inbound を受ける構成では、担当外のセッションが inbound ごとに破棄の記録を書くため、ログが際限なく増える、という指摘がありました。
ログにはローテーションも上限もありませんが、書き込みの負担より、どのセッションがどの理由で配送しなかったかが残る価値のほうが大きいです。
`DISCORD_NOTIFY_DEBUG` のような設定の裏に隠すと、障害のたびに設定を変えて再現を待つことになるため、拡張のログは常時記録します。

### 配送の直前に担当を再確認しない

スレッドの作成を待つ間に担当が変わると、配送の直前の判定は鮮度しか見ないため、変更前の担当のまま 1 件が通過する、という指摘がありました。

担当は Gateway のキャッシュから判定のたびに求めるため、変わるのは、チャンネルの改名や `access.json` の変更が、inbound の処理の数秒の幅に重なったときだけです。
通過した場合でも、宛先は変更前の担当チャンネル配下に作成したスレッドで、担当外のチャンネルや他のユーザーへは出ません。
その後の進捗の投稿は、毎回、投稿の直前に担当の判定を通過するため、2 件目以降は止まります。

発生条件が非現実的な経路のために判定を重ねると、分岐が増えて追いにくくなるだけです。

## 既知の制限

- ローカルの時計が 1 時間以上ずれていると、inbound の鮮度の判定によって、inbound が配送されません。
- 担当が未解決または曖昧なセッションでは、guild 宛の送信系ツールがすべて失敗します。
  意図した fail closed です。
- Gateway の `ready` より前に呼ばれた送信系ツールは、担当が未解決のため失敗します。
- ペアリングの応答は、全セッションから重複して送られます。
  公式の `gate` が、担当の判定より前に残るためです。
- 担当名に一致する `GuildText` が複数登録されていると、そのプロジェクトの guild への配送と進捗の転送が止まります。
  同名のチャンネルを整理するまで続きます。
- MCP だけを再起動すると、進行中のターンの進捗が、次の inbound まで止まります。
- 自分の Claude Code を特定できない環境では、進捗転送が無効になり、footer のモデル行も出ません。
  channel も無効と判定されるため、`CC_DISCORD_CHANNEL` で上書きします。
- SessionStart hook が実行されなかった場合、hook に `CLAUDE_PID` が渡らない場合、hook がプロセスの作成時刻を取得できなかった場合も、進捗転送が無効になります。
  このとき進捗スレッドも作成しないため、返信だけが親チャンネルへ届きます。
- 上流が `.mcp.json` の起動構造 (`bun run --cwd <プラグインのディレクトリ>`) を変えると、起動の中継の判定が一致しなくなり、進捗転送と channel が無効になります。
  取り込みの手順で、`.mcp.json` の差分を確認します。
- Claude Code がフラグ以外の方法で channel を有効にできるようになった場合、そのセッションは無効と判定され、`CC_DISCORD_CHANNEL` で上書きするまで、inbound を扱いません。
- Linux では、プロセスの作成時刻を `/proc/stat` の起動時刻から求めるため、時計の補正で値がずれると、後の `/clear` で書かれたポインタが採用されず、進捗転送が止まることがあります。
- macOS では、起動引数を `ps` の出力の空白で分けるため、空白を含むプラグインのディレクトリでは、自分の Claude Code を特定できません。
- Linux と macOS のプロセス情報の取得は、実機での確認が済んでいません。
- 進捗の投稿は、429 の待ち時間が 10 秒を超えると、送りません。
- 滞留スレッドの archive で閉じる直前に行う宛先の確認は、archive の要求を送る前の時点のものです。
  要求の処理中 (レート制限の待ちを含みます) にそのスレッドが宛先になると、閉じられることがあります。
  宛先は閉じられても終わらず、進捗スレッドは locked にしないため、次の進捗かリプライの送信で Discord が自動で再開します。
  [Discord の文書の Threads の節](https://docs.discord.com/developers/topics/threads)に、moderator が locked にしたスレッドを除き、メッセージの送信で自動で unarchive されるとあります。
- 5 時間枠と 7 日枠とモデル別枠の値は、直近 60 秒以内に試行済みの場合、最大 60 秒前の値になります。
  使用量 API の取得に失敗し続けた場合は、最後に取得できた値を表示し続けるため、遅れに上限はありません。
- inbound の後にそのセッションで行ったローカルの作業は、次の inbound、activation の切り替え、server の終了、12 時間のいずれかまで、同じスレッドへ転送されます。
  意図した挙動です。
  ただし、宛先のスレッドが archive されてから 4 時間を過ぎると、discord.js が既定の設定 (1 時間ごとの回収) でそのスレッドをキャッシュから除くため、12 時間より前でも進捗は送られなくなります。
  投稿の直前の担当の確認にはキャッシュにあるスレッドの親チャンネルが必要なので、キャッシュに無い宛先へは送りません。
  そのスレッドへリプライを送ると、スレッドがキャッシュに戻り、進捗の転送も再開します。
- 受領のリアクションは、進捗スレッドの作成の後に付きます。
  通常の遅れは 1 秒未満です。
